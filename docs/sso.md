# Вход через SSO (OpenID Connect)

Организация в Hearfolio Cloud может входить через **любого провайдера OpenID Connect**: корпоративный SSO, Keycloak,
Google Workspace, Okta, Entra ID, Tasker и т. д. Hearfolio — обычный relying party: он знает только стандарты (OpenID
Connect Core 1.0, Discovery 1.0, PKCE RFC 7636) и ничего не знает про конкретного провайдера. Всё, что отличает одного
провайдера от другого, приходит из его discovery-документа и настроек, которые вводит администратор организации.

Код: `backend/app/domains/sso/`, экраны — `frontend/app/features/sso/`. Сценарии продукта — [product.md](product.md).

## Как подключить провайдера (для администратора организации)

1. В Hearfolio: **Настройки → Вход и участники → Подключить провайдера**. Скопируйте «Адрес для возврата (redirect
   URI)» — вида `https://hearfolio.company.ru/api/v1/sso/callback/<id организации>`.
2. У провайдера зарегистрируйте **конфиденциальное веб-приложение** (client с секретом):
   - redirect URI — ровно скопированный адрес;
   - grant types — `authorization_code` и `refresh_token`; PKCE S256;
   - способ аутентификации клиента — `client_secret_basic` или `client_secret_post`;
   - scopes — `openid email profile`, плюс `groups`, если нужны правила по группам, и `offline_access`, чтобы провайдер
     выдавал refresh token (без него сеанс можно перепроверять, только пока жив access token — см. ниже).
3. Вернитесь в Hearfolio и заполните: адрес провайдера (issuer — ровно как провайдер себя называет, например
   `https://id.company.ru` или `https://tasker.company.ru/api/v1/oidc`), client id, client secret, scopes, подпись
   кнопки. «Проверить» скачает discovery, ключи подписи (JWKS) и проверит client id + секрет (Hearfolio отправляет
   заведомо неверный код: провайдер, принявший клиента, отвечает `invalid_grant`, не принявший — `invalid_client`).
   «Подключить» сохраняет; discovery проверяется ещё раз на сервере.
4. Настройте правила (ниже) и отправьте участникам **ссылку для входа** `https://hearfolio.company.ru/sso/<ключ>`.
   На странице входа есть и общая кнопка «Войти через SSO» (по рабочей почте — если у организации заданы домены — или
   по ключу организации).

Пример — Tasker: в Tasker создайте OIDC-клиента с redirect URI из шага 1, issuer — адрес OIDC-сервера Tasker (его
discovery лежит по `{issuer}/.well-known/openid-configuration`), scopes `openid email profile groups offline_access`.
Группы Tasker приходят в claim `groups` строками вида `corex`, `corex:dev`; Hearfolio сравнивает их как непрозрачные
строки.

Приложение Hearfolio (десктоп и телефон) входит через веб-страницу входа сервера, поэтому SSO там работает без
изменений: токен приложения, подтверждённый из SSO-сеанса, живёт и умирает вместе с ним.

## Правила организации

| Правило | Что делает |
|---|---|
| Способ входа | «Пароль или SSO» — оба способа открывают организацию. «Только SSO» — организация открывается только сеансом, полученным через этого провайдера; остальные получают `403 sso_required`, веб-приложение отправляет их на `/sso/<ключ>` |
| Владельцы входят и по паролю | Запасной вход для «Только SSO» на случай сбоя провайдера. Включить «Только SSO» (или выключить запасной вход, или сменить провайдера при «Только SSO») можно, только войдя через провайдера или оставив этот вход владельцам, — чтобы никто не запер организацию. Остальные правила меняются без этой проверки; суперпользователи сервера не ограничены |
| Кто может войти | «Только по приглашению» — входят существующие участники (добавленные или по приглашению). «Любой, кого пустит провайдер» — новый человек становится участником с ролью по умолчанию (участник или администратор, не владелец) |
| Домены почты | Только подтверждённая (`email_verified`) почта этих доменов. Проверяется при каждом входе и перепроверке |
| Группы провайдера | Нужна хотя бы одна из перечисленных групп в claim `groups`. Проверяется при каждом входе и перепроверке: исключили из группы — сеанс закончится на ближайшей проверке |
| Проверка у провайдера | Раз в сколько минут (5–60, по умолчанию 10) сеанс сверяется с провайдером |

Суперпользователи сервера проходят «Только SSO» всегда.

Аккаунты создаются только с адресом, который Hearfolio принимает: почта на служебных доменах (`.test`, `.local`,
`home.arpa`) проходит лишь при `ALLOW_LOCAL_EMAIL_DOMAINS=true`, иначе вход заканчивается ошибкой `email_invalid`.

## Как устроено (для разработчиков)

### Модели (`domains/sso/models.py`, миграция `0012_organization_sso`)

| Модель | Назначение |
|---|---|
| `SsoProvider` | 1:1 с организацией: issuer, client id, `client_secret_encrypted` (Fernet, `CryptoService`), scopes, подпись, кэш discovery (`metadata`), правила |
| `SsoIdentity` | `(provider, subject)` → пользователь; уникальны `(provider, subject)` и `(provider, user)`. `created_user` — аккаунт создан этим входом (у него нет известного пароля) |
| `SsoSession` | Сеанс Hearfolio, полученный через провайдера: `family_id` (семья refresh-сеанса), зашифрованные refresh/access токены провайдера, `access_token_expires_at`, `validated_at`, `check_started_at` (идёт проверка), `revoked_at` + `revoke_reason` |
| `SsoSessionToken` | Токен приложения (`UserToken`), подтверждённый из SSO-сеанса (`OAuthAuthorizationCode.session_family_id`) |
| `SsoLoginRequest` | Начатый вход: SHA-256 от `state`, `nonce`, зашифрованный PKCE verifier, хэш привязки к браузеру, `intent` (`login`/`link`), куда вернуться. Одноразовый, 10 минут; ежедневная задача `sso.purge_stale_login_requests` удаляет старые |

### Вход

1. `POST /api/v1/sso/start {organization_key | email, redirect}` (публичный) находит провайдера (по ключу или по
   домену из `allowed_email_domains`), создаёт `SsoLoginRequest`, ставит HttpOnly cookie `sso_browser` (путь
   `/api/v1/sso`, `SameSite=Lax`) и возвращает URL авторизации: `response_type=code`, `scope`, `state`, `nonce`,
   `code_challenge` (S256), `login_hint` для почты. `prompt=none`/`max_age` не используются.
2. Провайдер возвращает браузер на `GET /api/v1/sso/callback/{organization_id}` (вне OpenAPI). Проверки: state
   существует, не использован, не истёк, относится к этой организации; cookie браузера совпадает; `iss` в ответе (RFC
   9207), если есть. Обмен кода (`client_secret_basic`, иначе `_post`, с `code_verifier`), проверка ID-токена по
   JWKS (алгоритм из discovery, `kid`, ротация ключей — повторная загрузка JWKS при неизвестном `kid`): `iss`, `aud`
   (+`azp`), `exp`, `iat`, `nonce`, `at_hash`; затем userinfo (`sub` должен совпасть).
3. Пользователь: по `(provider, sub)`; иначе — существующий аккаунт с той же почтой, **только если `email_verified`**;
   иначе — новый аккаунт, если правила разрешают вступление (тоже только с подтверждённой почтой). Проверяются домены и
   группы; неучастник без права вступить получает `not_member`.
4. Сеанс: обычные cookie (`AuthService.start_session`) + `SsoSession`. Редирект на `redirect` (только same-site пути,
   например `/oauth/authorize?...` для приложения), иначе `/home`. Ошибки возвращаются на `/sso/<ключ>?sso_error=<код>`
   (привязка из профиля — на `/settings/profile?sso_error=`), тексты на русском — во фронтенде (`useSso.ts`).

Привязка из профиля (`POST /api/v1/sso/link`) идёт тем же путём с `intent=link`: аккаунт провайдера привязывается к
текущему пользователю без требования совпадения почты, и браузер сразу получает SSO-сеанс, если правила это позволяют.
Отвязка (`DELETE /api/v1/sso/identities/{identity}`) завершает SSO-сеансы этой привязки; единственный способ входа
аккаунта, созданного через SSO, отвязать нельзя (`409 only_sign_in`).

### Сеансы и проверка у провайдера

Back-channel logout **не используется** (решение владельца). Отключённый у провайдера человек теряет доступ ленивой
перепроверкой:

- Каждый запрос с учётными данными проходит `SsoSessionService.guard` (`core/auth.py`): это SSO-сеанс? (кэш в памяти
  процесса на `SSO_SESSION_CACHE_SECONDS`, 30 с — обычные парольные сеансы стоят один запрос к БД за окно).
- Если последняя успешная проверка старше интервала организации, **один** запрос забирает проверку атомарным
  `UPDATE … WHERE check_started_at IS NULL OR < now-60s` (работает между процессами); остальные идут дальше с тем, что
  в БД. Так refresh token провайдера, который ротируется и строго проверяется на повтор, никогда не предъявляется дважды.
- Проверка: `refresh_token` grant → новый refresh token сохраняется сразу (compare-and-swap по старому шифротексту),
  до использования результата; ID-токен из refresh проверяется без `nonce`, но с `sub`; затем userinfo с новым access
  token. Без refresh token — userinfo со старым access token, пока он не истёк.
- Явное «нет» (`invalid_grant`, userinfo 401/403, другой `sub`, правила доменов/групп больше не выполняются) —
  сеанс завершается сразу: семья refresh-токенов отзывается, токены приложений из него удаляются, кэш сбрасывается;
  следующий запрос получает 401, веб-приложение уходит на страницу входа.
- Провайдер недоступен (таймаут, 5xx, 429), `invalid_client` (сломалась наша настройка) или access token истёк без
  refresh token — это не вердикт о человеке: сеанс работает до `SSO_REVALIDATE_GRACE_SECONDS` (24 ч) после последней
  успешной проверки, потом нужен новый вход (`revoke_reason` `provider_unavailable` / `reauth_required`).
- `POST /auth/refresh` делает ту же проверку для своей семьи; `POST /auth/logout` завершает SSO-сеанс.

Ограничение: если сеть оборвалась после того, как провайдер уже повернул refresh token, у Hearfolio остаётся старый —
следующая проверка получит `invalid_grant` и человек войдёт заново. Это безопасный исход.

### Безопасность запросов к провайдеру

`OidcClient` (`services/oidc_client.py`): только `https://` (`http://localhost` — при `DEBUG`), никаких адресов
внутренней сети без `SSO_ALLOW_PRIVATE_ISSUERS=true` (проверяется каждый URL из discovery), без редиректов, таймаут
`SSO_HTTP_TIMEOUT_SECONDS`, ответ не больше `SSO_MAX_RESPONSE_BYTES`. Проверка DNS — по месту, без защиты от
DNS-rebinding после проверки. Секрет клиента и токены провайдера хранятся зашифрованными (`ENCRYPTION_KEY`) и никогда не
отдаются API.

### Настройки сервера

| Переменная | По умолчанию | Что |
|---|---|---|
| `SSO_HTTP_TIMEOUT_SECONDS` | 5 | Таймаут запросов к провайдеру |
| `SSO_MAX_RESPONSE_BYTES` | 524288 | Наибольший ответ провайдера |
| `SSO_ALLOW_PRIVATE_ISSUERS` | false | Разрешить провайдера во внутренней сети |
| `SSO_REVALIDATE_GRACE_SECONDS` | 86400 | Сколько сеанс живёт без ответа провайдера |
| `SSO_LOGIN_REQUEST_TTL_SECONDS` | 600 | Время на вход у провайдера |
| `SSO_JWKS_CACHE_SECONDS` | 3600 | Кэш ключей подписи |
| `SSO_SESSION_CACHE_SECONDS` | 30 | Кэш «это SSO-сеанс?» в процессе |

`PUBLIC_URL` должен быть задан за прокси: из него строятся redirect URI и ссылка для входа.

### Тесты

`backend/app/domains/sso/tests/` — фейковый провайдер на `httpx2.MockTransport` (RSA-ключи генерируются в тесте,
discovery/JWKS/token/userinfo, ротация refresh token со строгим обнаружением повтора, issuer с путём): вход,
подделанные подпись/iss/aud/nonce/exp/state, другой браузер, `email_verified=false`, привязка по `sub`, правила
вступления, «Только SSO», перепроверка (отключённый пользователь, потеря группы, провайдер недоступен → льготный
период → новый вход, истёкший access token без refresh token, одна проверка на сеанс при параллельных запросах),
токены приложения, секрет не попадает в ответы, SSRF-защита.
